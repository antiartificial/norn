# Protected M6 staging app rollback

This source adds a `staging-rollback` lane to the reusable Norn app release workflow. It restores only an earlier successful staging deployment with an exact deployment UUID, source SHA, and OCI digest. The Norn API rechecks its durable GitHub release candidate, current InfraSpec binding, immutable artifact attestation, and a different current deployment before queuing the rollback. No Nomad job write occurs in the workflow.

The lane is inactive until a caller on the protected default branch pins the merged reusable workflow by its **full commit SHA**, and the staging control API runs a signed release containing this handler. The staging GitHub OIDC policy must allow the pinned reusable workflow, `workflow_dispatch`, `release:rollback`, the exact app/repository binding, and the staging environment. Do not use a relative reusable workflow reference; the exchange requires a SHA-pinned `job_workflow_ref`.

The private one-use Linux runner must have labels `self-hosted`, `Linux`, `X64`, `norn-fleet-protected`, and `norn-work-staging-fleet-effect`. Register it with the exact name `norn-m6-<run_id>-<run_attempt>` after the dispatch exists; the job checks this name before reading the private route or obtaining a token. Provide the existing CA file at `/etc/norn-fleet-executor-api-route/ca.pem` and its reviewed SHA-256 in `NORN_FLEET_RUNNER_API_CA_SHA256`. The staging `NORN_API_URL` must be `https://localhost:18443`. Retire the runner after this one job.

The dispatch must supply `lane: staging-rollback`, `rollback_environment: staging`, `runner_private: true`, `rollback_confirmation: ROLLBACK`, the exact admitted target, an existing database-backed record ID, and the reviewed SHA-256 of `/route-proof`. Set `NORN_MANAGED_MYSQL_PUBLIC_URL` to the pathless HTTPS origin of the managed app. The job reads that record and route proof before and after, samples public `/version` every two seconds while Norn operates, records non-200 samples, and accepts only a successful durable Norn operation. Sample counts are evidence of measured interruption, not a zero-downtime guarantee.

Before activation, the managed MySQL InfraSpec still needs a reviewed real hostname, active catalog declaration, provisioned Nomad Variables, and a successful Norn-owned staging deployment of version A followed by version B. Its current source declaration is disabled with a `.invalid` origin. The older direct Nomad pilot does not qualify as the rollback target. If schema or writer-floor changes are incompatible with version A, use a compatible pair or forward repair; do not force an old binary or image back into service.
