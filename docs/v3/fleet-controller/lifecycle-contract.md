# Fleet controller lifecycle contract

Status: WP1 deliverable for [`plan.md`](./plan.md). This records the current
(pre-WP2+) behavior of the three attempt implementations described in
plan.md §1, as a single reference with an owning regression test per fact.
It changes no behavior. Every test name below was verified to exist with
`go test -list '.*' ./handler ./store ./etcdstore . | grep -i fleet` (or, for
the four names this WP adds, a direct `go test -list` match) on
`v2/api` at the branch head. "None" in the test column is itself a finding:
it means the audit found no regression pinning that fact, not that the fact
is false.

## 1. Routes × backend

Paths are `/api/v1/fleet/...` unless noted. "PG" is the live legacy path
(plan.md §1.1); PG V3 (`fleet.RunnerAttempt`, `handler/fleet_attempts.go`) is
unrouted and out of scope for this table except where named explicitly.
Fleet-adjacent routes outside plan.md §1.2's `/api/v1/fleet/...` scope are not
listed: etcd `GET/PUT /api/v1/apps/{id}/fleet-target`
(`etcd_fleet_runtime.go:145,150`) and the PG authority-only
`/api/v1/apps/{id}/external-deployments/{begin,resume,admit}` (`main.go:2173-2175`).

## 1b. Phases, approval rule and error codes (plan.md §1, WP1)

This table adds the three facts §1's table has no room for: which phases a
route can read or advance, the exact authorization/signed-acceptance chain
(not just the credential boundary's scope name), and every HTTP
status/error-code pair the route can return. It is keyed to the same rows as
§1, in the same order. It changes no behavior and does not touch §1's
owning-test citations.

**No environment-reviewer or independent-review gate exists anywhere in this
surface** (proposal.md §1.5, "Not enforced"; confirmed by
`grep -rln 'reviewer\|RequiredReviewer\|EnvironmentProtection' handler/ store/ etcdstore/`
excluding tests, which returns no files). No per-row note repeats this.

**Shared baselines**, cited by letter instead of repeating per row:

- **A — authentication/scope, every route.** PG: 401 `authenticated_principal_required`, 403 `insufficient_scope` (`requireControlScope`, `handler/handler.go:301-312`; `requireFleetOperateScope`, `handler/handler.go:317-328`). etcd: 401 `unauthorized`, 403 `insufficient_scope` (`etcdManagedTokenAuth`, `etcd_source_validation.go:148-168`).
- **B — `requireFleetGitHubPlan`, every PG `github/*` route.** 503 `fleet_github_not_configured` (`handler/fleet_github.go:979`), 503 `fleet_plan_store_unavailable` (`:983`), 400 `invalid_fleet_plan_id` (`:991`), 404 `fleet_plan_not_found` (`:996`), 500 `fleet_plan_read_failed` (`:1000`). Requires scope `api:write` (`:974`).
- **C — signed-acceptance surface, every route that queues through `h.pipeline`/`writeOperationAcceptanceError`.** 410 `idempotency_window_expired`, 409 `idempotency_key_reused`, 409 `legacy_idempotency_ambiguous`, 409 `operation_admission_rejected`, 503 `operation_acceptance_indeterminate`, 503 `operation_acceptance_unavailable`, 500 `operation_acceptance_failed`, 503 `snapshot_execution_unavailable`, 503 `evidence_reserve_exhausted` (`handler/control_protocol.go:174-227`). Two further error families are reachable only from this surface when the queued operation kind is `fleet.runner-attempt` or `fleet.reconciliation` (`store.FleetRunnerAttemptAdmissionError` / `store.FleetReconciliationAdmissionError`, `control_protocol.go:185-201`); they are listed under the attempts/reconciliations rows below, never under capacity-plan/pull-request/dispatch/rerun, whose operation kinds cannot produce them.

## 4. Dead legacy code (plan.md §1.1)

`RetryFleetRunnerAttempt`, `FailFleetRunnerAttempt` and `InsertFleetReconciliation`
(`store/fleet_runner_attempts.go:169-310`) have no production caller — the
live PG path reaches these states through the signed checkpoint/acceptance
path instead. They remain exercised only by tests
(`TestFleetRunnerAttemptLifecycle` calls `RetryFleetRunnerAttempt` and
`InsertFleetReconciliation`; `TestFleetRunnerPilotRunMigrationRoundTrip` calls
`FailFleetRunnerAttempt`). This plan does not fence them and WP2+ must not
remove their test coverage without first confirming they stay dead.

## 5. Pre-existing defect (plan.md §1.6, H4/M6)

In `DispatchFleetGitHubApply`, `MarkFleetGitHubDispatchSubmitting` runs at
`handler/fleet_github.go:857`, immediately before the one permitted GitHub
POST. If that POST then fails with `githubapp.ErrDispatchPreSubmit`, the
handler calls `DeletePreparedFleetGitHubDispatch` (`fleet_github.go:867-869`).
That delete matches only `dispatch_state='prepared' AND run_id=0`
(`store/fleet_github_dispatches.go:128`), so against the `submitting` row it
just fenced it is a no-op: no error, zero rows affected. The row is left
`submitting` with `run_id=0`. The only store function that resets a
`submitting` row to `prepared` is `ResetFleetGitHubDispatchPreSubmit`, which
exists for the distinct external-Mac execute lane
(`handler/fleet_github.go:~555`) and is never called from this path. Later
calls therefore observe an ambiguous dispatch (`fleet_github_dispatch_ambiguous`)
until the WP2.2 abandon path resolves it.

This is recorded, not fixed, per decision H4 (plan.md §5): "Leave behavior
unchanged. Pinned by `TestDispatchPreSubmitFailureLeavesSubmitting`." That
test (new, this WP) reproduces the exact store-call sequence above and
asserts the row stays `submitting`. It pins the store semantics only: it does
not drive `DispatchFleetGitHubApply` (whose `*githubapp.Client` field has no
test seam), so a handler-only switch to `ResetFleetGitHubDispatchPreSubmit`
would not fail it. Whoever makes that fix must update this test and add a
handler-level check in the same change (WP6's HTTP-boundary suite is the
natural home).

## 6. Same-plan concurrent executor gap (Q11, plan.md §5)

On the PG legacy path, recovering a source attempt
(`RecoverFleetRunnerAttempt`, `store/fleet_runner_attempts.go:316`) cancels a
still-live source "superseded by verified recovery workflow" **without any
proof that the source's GitHub run has actually stopped** (plan.md §1.4,
"Recovery" row). It only requires the caller's authority-consumption tuple to
match (`authorityMetadataMatches`, `handler/fleet_runner.go:549`). A second,
still-running executor from the superseded run can therefore keep mutating
provider state concurrently with the new recovery attempt, with no lineage
check preventing it (`validateFleetRunnerAttemptLineage` on PG legacy is a
no-op; it only derives the root — plan.md §1.4, "Lineage validation").

There is no current regression test that could pin a fix here, because there
is nothing to pin: this is an absence of a check, not a behavior. Decision
Q11 (plan.md §5) accepts a provisional default — once a plan's target is
registered (WP3+), legacy recovery is refused unless the source attempt's
GitHub run is proven `completed` via the WP5 observers
(`fleet_target_recovery_requires_stopped_source`). Unregistered targets keep
today's unchecked behavior; this contract records that gap so later work
does not treat it as newly introduced.
