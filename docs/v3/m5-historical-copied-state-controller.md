# M5 historical copied-state controller

The protected `m5-historical-copied-state.yml` workflow is pinned to the Mini transition from signed source `3da50fe3a3c9f37d64e24c03a7dcfea94153da58` to signed target `3602e7e3d5fe5c0ef333b4041580d48ec15b24c5`. It runs only from protected `master`, in `m5-mini-release-rehearsal`, on a dedicated macOS ARM64 runner labeled `norn-m5-isolated`. The runner must carry owner-only copies of the historical backup, proof, completed shadow receipt, both signed releases, and the pinned release public key. The protected environment variables name those paths. No backup bytes or credentials are uploaded to GitHub.

Before enabling the runner, install a root-owned, runner-immutable isolation checker at the path configured by `M5_ISOLATION_CHECK`. It must fail unless production network egress is denied, only the disposable local database and loopback API are reachable, no live Mini/Fleet credentials are present, and the runner is dedicated to this job. The workflow fails if the checker is absent. The runner operator must attest this host boundary; a GitHub runner label alone is not isolation evidence.

The controller verifies both signed releases, the historical backup/receipt binding, and the isolation checker before creating a new private restore and signed shadow LaunchAgent receipt. The private-copy helper admits the historical pair only with `NORN_M5_HISTORICAL_ISOLATED=1`, the exact old shadow receipt and target SHA, and no `NORN_DATABASE_URL` or audit key. Its normal fresh transition path still uses the one-hour protected-backup verifier. The historical helper only restores to a socket-only disposable PostgreSQL server, runs candidate migrations and passive checks, and compares original table fingerprints. It does not switch the live Mini release or replay the consumed transition journal.

This workflow proves a new isolated restore and signed target shadow run once its receipt is reviewed. It does not close M5 by itself. A separate protected controller step must still exercise the durable upgrade and admitted rollback or signed forward-recovery boundary against the disposable copy, compare source and target workload IDs/routes/periodic schedules, and measure application requests separately from API interruption. Retain both the new receipt and the runner isolation attestation until that step is complete.
